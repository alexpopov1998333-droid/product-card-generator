# AI-помощник для подготовки товарных описаний

Прототип сервиса, который по данным контрольно-измерительного прибора собирает черновик карточки товара для B2B-каталога. Принимает JSON или форму, зовёт LLM через API, отдаёт готовые блоки и отдельно показывает, каких данных не хватает.

Тестовое задание для вакансии AI-разработчик, СОЮЗ-ПРИБОР.

## Что делает

На входе данные прибора: название, производитель, характеристики, описание или фрагмент паспорта. На выходе:

- SEO-заголовок до 70 символов
- SEO-описание 800–1200 символов
- структурированный список характеристик
- 3–5 поисковых запросов
- блок для менеджера, кому подходит прибор и какие задачи решает
- список полей, которых не хватило

Главное требование задания: модель не выдумывает технические характеристики. Оно закрыто не только промптом, но и проверкой после ответа, подробности ниже.

## Быстрый старт

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # вписать свой ключ
uvicorn app:app --host 127.0.0.1 --port 8088
```

Открыть http://127.0.0.1:8088/, вставить JSON и нажать кнопку.

Переменные окружения:

```
LLM_API_KEY=sk-...
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
LLM_TIMEOUT=90
```

Ключ лежит только в `.env`, файл в `.gitignore`. Подойдёт любой OpenAI-совместимый провайдер, достаточно поменять `LLM_BASE_URL` и `LLM_MODEL`.

Примеры в `examples/` получены на модели DeepSeek через OpenAI-совместимый шлюз, имя модели видно в поле `meta`. По умолчанию `.env` настроен на официальный `api.deepseek.com` и `deepseek-chat`, код от провайдера не зависит.

## API

`POST /api/generate`, тело это объект прибора.

```json
{
  "name": "Манометр показывающий ДМ 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Ответ:

```json
{
  "seo_title": "...",
  "seo_description": "...",
  "specs": [{"name": "...", "value": "..."}],
  "search_queries": ["..."],
  "commercial_block": "...",
  "missing_fields": ["..."],
  "warnings": ["..."],
  "meta": {"model": "...", "seconds": 5.3, "title_len": 65, "description_len": 1011}
}
```

Ошибки:

- 422, если `name` пустой, `specs` не объект или на входе не объект JSON
- 502, если LLM недоступна, вернула не JSON или ответила ошибкой
- 500, если не задан ключ

`GET /health` для проверки, что сервис поднялся.

## Как закрыто требование «не выдумывать характеристики»

Три слоя, каждый проверяется тестами.

1. Промпт. Системная инструкция прямо запрещает добавлять факты, требует помечать отсутствующее и возвращать строгую JSON-схему. Ответ запрашивается в режиме `response_format: json_object`, поэтому парсинг предсказуемый.
2. Проверка ответа. Каждое значение из `specs` сверяется со входом по числовым и буквенно-цифровым токенам. Выдуманное значение не выбрасывается молча, а заменяется на «данных нет» и попадает в `warnings`. Характеристики, которые модель пропустила, но которые есть во входе, добавляются обратно, чтобы ничего не терялось.
3. Свод пропусков. Группы, важные для прибора (диапазон, класс точности, питание, выход, корпус), проверяются по входу отдельно. Список от модели сводится с ними без дублей и обрезается до восьми пунктов, иначе контент-менеджер получает простыню.

Дополнительно проверяются длины: заголовок при переполнении сначала просится переписать короче, и только потом обрезается; описание при выходе из 800–1200 символов уходит на один повторный запрос с указанием фактической длины.

## Промпт и решения

Промпт лежит в `core.py` в константе `SYSTEM_PROMPT`, его видно целиком. Решения, которые стоит объяснить:

- **Факты только из входа.** В системном промпте отдельным пунктом запрещено добавлять диапазоны, материалы, страну и аналоги. Это главный критерий проверки задания.
- **JSON-режим вместо парсинга текста.** Меньше веток на разбор, не нужны регулярки по Markdown.
- **Постпроверка вместо доверия модели.** Даже с хорошим промптом модель иногда добавляет «нержавеющая сталь». Проверка ловит это детерминированно, без второго вызова LLM.
- **«Данных нет» вместо удаления.** Контент-менеджер видит пробел в карточке, а не пустое место.
- **Ретраи только по длине.** Заголовок и описание имеют формальные лимиты, их дешевле поправить вторым запросом, чем обрезать текст.
- **Без базы и деплоя.** По условиям задания нужен локальный прототип, поэтому ни Postgres, ни очередей, ни авторизации.

## Примеры

- `examples/product1_dm2010sg.json` — манометр сигнализирующий ДМ2010Сг. Заголовок 65 символов, описание 1011, 13 характеристик, 5 запросов, 5.3 с.
- `examples/product2_pd100.json` — преобразователь давления ОВЕН ПД100-ДИ0,4-115-0,5. Заголовок 61 символ, описание 1029, 16 характеристик, 5 запросов, 6.8 с.

Входные данные в `input/` сняты с открытого каталога souz-pribor.ru, ссылки на страницы товаров есть в самих файлах. У манометра производитель на странице не указан, поэтому в примере он честно попадает в `missing_fields`.

Скриншоты интерфейса: `docs/01-form.png`, `docs/02-result.png`.

## Тесты

```bash
pytest -q
```

13 тестов, живые вызовы LLM не нужны, модель подменяется заглушкой. Покрыто: выдуманная характеристика помечается, характеристики из входа не теряются, длинный заголовок сокращается с ретраем, короткое описание даёт предупреждение, пустые и некорректные поля дают 422, API отдаёт карточку.

## Ограничения

- Нет базы, истории и авторизации, по условиям задания это не требовалось.
- Один товар за запрос, пакетной обработки нет.
- Проверка значений сравнивает токены, поэтому теоретически пропустит выдуманное значение, все цифры которого случайно есть во входе. Для прототипа это приемлемо, в продакшене нужна сверка по структурированному паспорту.
- Качество SEO-текста зависит от модели, промпт не гарантирует уникальность между похожими товарами.
- Нет кеша и учёта стоимости запросов, каждый вызов платный.
